## 1. 已确认事实与决策

参考源：[UNSA-studio/xdyl 固定提交 fe87767894edfcbc818101bf87a11c1b0501dc49](https://github.com/UNSA-studio/xdyl/tree/fe87767894edfcbc818101bf87a11c1b0501dc49)。详细证据及现有六接口见 [CHAT_V1.md](api/CHAT_V1.md)；目标契约见 [CHAT_V2_PROPOSAL.md](api/CHAT_V2_PROPOSAL.md)。

| 发现 | 影响 | 单靠 iOS 是否能修复 |
| --- | --- | --- |
| Android 未携 Bearer，Worker 不读 body token | 照搬后无法认证；不能靠取消鉴权解决 | 能正确携带认证，不能修复其他客户端 |
| 仅列前 200 条，再按客户端时间过滤 | 旧消息阻塞新消息、同毫秒/迟到漏信 | 不能，需要新同步契约 |
| KV 先 get 再 put，幂等键包含 ts | 并发、重试和改时间可能重复 | 不能，需要原子幂等 |
| 每账号一把无版本公钥，按 Android 版本选曲线 | 两类算法不互通、换机覆盖、旧历史失密钥 | 不能，需要设备及密钥版本 |
| read 仅鉴权后返回成功 | 无真实送达或已读 | 不能，需要回执存储与同步 |
| 消息 TTL 30 天，无发件同步 | 不是完整云历史，多设备不可恢复 | 不能，需要明确保留策略和副本 |
| 无推送注册和触发逻辑 | iOS 挂起后无法靠轮询收信 | 不能，需要在线服务调用 Bark |
| 全局本地游标只保存当前会话、账号数据混用 | 丢其他联系人消息或串账号 | 可在新客户端修复，但不能抵消服务端漏洞 |

曾匿名验证 HTTPS ping 可达，不等于验证部署版本或认证/消息正确。本轮测试使用合成身份/密钥及模拟Bark，未做真实账号、Bark 或线上业务写操作。用户提供压缩包原件 SHA256 为 `dcecebea81a92ea56db7b298c5652c60d88e64a34a6f6d97d00b842d4a9b4e5d`；原 index SHA256 为 `c4c571bacd80d47488db918fee9f0b6cf70a13c61913275867f199342a927438`。原件保持不改，新实现单独目录。

选择“V1 原地补字段”虽开发量较小，但会保留单公钥、时间游标和旧客户端错误假设；选择“版本化 V2”成本更高、需各端升级，却能独立定义可靠同步和设备身份。采用后者，依据见 [ADR-0001](adr/0001-chat-v2-before-ios-migration.md)。

## 2. 整改分组与交付责任

### P0：在线迁移的阻塞项

1. **身份与权限**：主站稳定账号 ID，统一 Bearer，聊天短期设备会话；仅从认证信息确定发送人。移除 token query、HTTP 降级、错误堆栈和敏感日志。设备撤销令牌立即失效；主站账号身份不明确时拒绝，不回退昵称。
2. **可靠持久化**：原子保存消息、设备投递事件、幂等结果和通知 outbox；唯一约束处理并发，不靠 KV get-then-put。事务可见顺序与游标顺序一致；未提交、回滚的写入不能形成永久漏信窗口。
3. **同步**：真正遍历分页，以服务端事件顺序和绑定设备的游标推进；任意会话事件都先落盘再 ack。支持断线、重复读取、保留期过期后的明确重同步与历史缺口。
4. **密钥及设备**：V2 每设备两算法、公钥版本与 CAS，消息携双方 key ID；发送覆盖完整密钥快照，版本变化重取确认。提供设备撤销与指纹变化提示；不能以首次 GET 取代服务端 CAS。
5. **密码学互操作**：两算法 DER/HKDF/AAD/AES-GCM 的跨端测试向量，非 ASCII/长文字、篡改、错误 tag/nonce 验证。文档设计须经复核后才能编码；不能把 V1 密文接到 V2 接口。

### P1：完整可靠性方案的功能门槛

1. **回执**：设备接收与用户已读分开；ack/read 幂等、单调、受参与人权限约束。服务端接受、Bark 接受均不等于设备收信或已读。
2. **Bark**：绑定/解绑/测试/状态，消息持久化后通过 outbox 触发；通用通知不包含聊天正文或账号信息。私聊失败与推送失败分别诊断，Bark 故障不能使发送消息失败。
3. **运维及隐私**：超时、429、配额、存储容量、清理任务、失败 outbox、备份恢复、设备撤销和异常监控。日志仅记录 request ID、脱敏错误码、计数、耗时，不记录 token、Bark key、明文、密文或私钥。
4. **兼容发布**：V2 capability 只声明本地已实现且配置可用能力。后续用户要求旧安卓互聊，已实现显式主设备/双编解码适配；不在中继解密，不向原生V2路径混入V1密文。兼容36d3a8c的Bearer+seq，不为早期无认证APK取消鉴权，不承诺搬迁旧私钥或强删其本地历史。

中继维护方负责服务实现、存储/部署选择、运维和测试环境；主站维护方需确认稳定身份与凭证验证行为；Android 维护方负责 V2 升级；后续 iOS 负责原生页面、本地安全存储、生命周期及联调。本文不赋予本项目操作这些外部系统的权限。

## 3. 存储与部署约束

不强制维护方迁移云厂商；契约约束的是事务、顺序、权限和保留行为：

- 继续 Worker 路线，可评估 D1 的事务批处理及序列化写入；KV 只作可丢弃缓存，不能作为强幂等/有序消息的唯一真相源。
- VPS 路线，可用具备事务和唯一约束的 SQL 存储；须验证并发提交顺序，而不只检查有无自增列。
- 不在本次文档中宣称任一路线已部署或免费够用；上线前按预估设备数、日消息量、每消息副本、保留30天、索引和备份估算容量与请求成本，记录平台配额。
- 最小持久模型：账号映射、设备/会话、版本化公钥、消息、每设备事件流/接收水位、每会话已读水位、幂等 tombstone、Bark 绑定及 outbox。所有权与外键以稳定账号身份为基础。
- 事件与正文默认保留30天；清理后应使旧游标显式过期，不能悄悄略过缺口。幂等 tombstone 保留设备存续期，仅存最小请求指纹及结果。设备/账号删除后另执行受控清理，不许以重建同一身份重放旧请求。
- seq 分配、消息与事件提交须受一致的序列化边界保护，防止事务 A 取较小序号未提交而 B 已被客户端读取。若开启读副本，须保证单调一致的游标读取，不把副本延迟当成“已同步”。

技术依据：[Cloudflare KV 一致性说明](https://developers.cloudflare.com/kv/concepts/how-kv-works/)、[D1 限制](https://developers.cloudflare.com/d1/platform/limits/)、[D1 batch 事务说明](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)。这些是设计参考，不是选型或性能验收结论。

## 4. Bark 接入与边界

收信流程：消息事务提交 → outbox → 在线 worker/任务消费者 → Bark `/push` → Bark 的 APNs → 用户安装的 Bark App。不是“iOS 被通知后偷偷轮询”，也不依赖本 IPA 拥有 APNs 签名能力。

- 用户主动绑定 Bark key；服务端加密保存，解绑和撤销设备清除待发任务。不将主站 access token 传给 Bark。
- 仅推“收到新私聊，请打开应用查看”，无正文、发送者姓名或尚未实现的 App 深链；不宣称通知能打开具体聊天。
- 当前只支持官方 `https://api.day.app`，拒绝所有自建主机、路径/query/userinfo/非默认端口与重定向；没有实现任意自建主机的DNS/IP白名单能力。
- 持久 outbox 使用逻辑去重和租约；按个人已读/删除/屏蔽/过期过滤，单纯设备ack不等于已读，不能吞掉静默后的未读摘要。Bark 不提供这里可保证的端到端 exactly-once，网络超时重试仍可能重复提醒。
- 测试成功分“排队 / Bark 接受 / 手机上实际显示”三步；最后一步需要真机验收。通知点击/到达不触发已读。
- Bark 不是密钥备份、消息存储或聊天加密的替代品；多设备推送仅指提醒各设备，不代表新设备能解密旧历史。

详细请求、错误、重试次数与期限统一以 [V2 契约](api/CHAT_V2_PROPOSAL.md)为准；实际部署版本的 Bark JSON 需在隔离测试环境验证。

**下表是完整验收目标，不代表全部完成；本地验证记录见第7节，生产/真机项仍待测。** 测试用隔离部署、合成账号；不得向生产服务批量发送消息或真实凭证。每条记录环境/服务提交、客户端版本、时间、步骤、预期、脱敏结果及通过/失败；密码学向量只用测试密钥。

| AUTH-03 | A 查询/ack/read B 的设备或会话；撤销设备后复用令牌 | 403；无副作用，撤销后新请求不能成功 |

| SEND-01 | 同请求并发20次；服务提交后丢响应再重试 | 同message_id，单条逻辑消息、每设备单逻辑事件及outbox |

| RECEIPT-01 | 仅server接受、仅Bark接受、仅设备ack | 分别显示正确状态，均不得显示已读 |
| RECEIPT-02 | 重复/倒退/越界read，另一账号read | 水位单调、无重复逻辑回执；越界400、越权403 |
| BARK-01 | 绑定、测试、解绑、撤销与任务并发 | 无key读回/日志；状态可查；解绑后待发取消，不能撤销在途通知须说明 |

## 6. 后续 iOS 实施约束（尚未实施）

- 保持五标签，在社区内提供“论坛 / 私聊”切换；社区显示聊天未读，“我的”仍显示原业务通知，两个计数不混用。
- 仅原生文字私聊、联系人备注、本地历史和发送状态；备注独立于服务器昵称。没有群聊、图片、语音或通话。
- 明确第三方中继及首次主站凭证用途，默认不联网，用户同意后启用；更换主机重新确认。拒绝 HTTP 和跨源令牌转发。
- 按稳定账号与中继隔离数据库、游标、密钥、未读和草稿；私钥在 Keychain，历史加密且受文件保护。登出停止连接并隐藏数据，保留本地历史，清理需明确确认；清历史与删密钥分开，说明后者影响旧消息。
- 前台统一同步全部会话，后台立即停；回前台先补拉。未来可默认8秒单任务轮询、分页连续补齐，临时错误退避；不得移植 Handler 遗留轮询。Bark 依赖服务端，不延长 iOS 后台执行。
- V2 多算法按目标设备协商，不使用 V1 的账号级切换冒充双算法同时兼容；V1 公钥不被新客户端覆盖。已有密钥/设备需要用户明确迁移，不可静默接管。
- 消息持久化与游标原子更新，原请求幂等重试；换账号/中继、退出或撤销使旧响应失效。错误保持草稿与历史，不显示“发送成功”掩盖失败。
- 适配 iOS16/26、键盘与安全区、大字体、深浅色、VoiceOver；输入区不被键盘遮挡，消息可滚动阅读。实际实施时再同步 UI 规范并进行真机验收。

这些是后续迁移边界，不代表本 App 已有聊天存储、加密、Bark 或任何 `/chat/v2/` 调用。
